# Stage 3 双三槽帧池原样复制实施计划

> **实施约定：**按任务顺序执行，每个任务在仿真或构建关口通过后再进入下一任务。新工程以已上板验收的 `stage3_frame_pool_gate_fix` 为源；实施前记录其源文件和位流哈希。截至 2026-10-20，软件集成和候选位流已完成，实板验收待进行；下文保留实施过程和未完成的验收项。

**目标：**在独立 PDS 工程中接通 `HDMI 输入 → 输入三槽帧池 → RGBX8888 原样帧复制器 → 输出三槽帧池 → HDMI 输出`，完成 1280×720@60 Hz 上板验收。

**架构：**两个 `frame_pool_manager` 由 DDR 时钟域内的 `frame_pipeline_ownership` 调度。DDR3 的采集写、复制读、复制写、显示读四类请求分别经写端与读端仲裁；复制器只处理已发布的完整输入帧，并在完整输出帧写入排空后发布。显示端仅在帧边界取得输出池 READY 槽。

**工具与格式：**PG2L200H、PDS 2022.2-SP6.4、Vivado Simulator 2020.2、Verilog、PowerShell；RGBX8888 为 `{R,G,B,8'h00}`；DDR 数据端口 256 位、地址单位为 32 位字。

## 全局约束与已知事实

- 用户已确认 `stage3_frame_pool_gate_fix` 修正版运动画面连续运行至少 30 分钟并通过上板验收。保留这份工程和阶段 2 RGBX8888 位流为可回退版本；新的板级结果另行记录。
- 实施前，稳定工程的实时顶层 `fram_buf.v` 只有采集与显示共用的一个三槽池；本计划在独立副本中接入双池。
- `frame_pool_address.v` 使用六个 `2^22` 字槽，输入槽 0–2、输出槽 3–5。每帧有效区为 `1280×720 = 921600` 字，即 `115200` 个 256 位数据拍；每行 `160` 拍。16 拍突发时每行恰好 10 个突发，每帧 7200 个突发。
- 四条整帧数据流在 60 帧/秒时的有效载荷为 `4×1280×720×4×60 = 884736000 B/s`。该值不含 DDR 仲裁、刷新和突发间隙，板上吞吐须实测。
- Pango DDR3 IP 没有可用的读 `RREADY`，也没有标准 AXI 写 `BVALID`。发出读地址前必须为全部返回拍预留接收空间；写端须在来源请求排空且按写 ID 统计的完成事件结束后才能发布帧。
- 帧池管理和槽号保持在 DDR 时钟域。输入/输出像素时钟域只传同步事件或经异步存储跨域的数据，不直接取样多位槽号。
- 输出 HDMI 时序固定 1280×720@60 Hz。处理完成的不同帧数、重复显示数、READY 回收数分别计量。

## 实施顺序与停机点

1. 工程副本与事务契约通过后，开始实时采集/显示适配。
2. 读端接收空间、写端所有者与排空判据分别通过故障注入后，接通复制器。
3. 整帧逐字比对通过后，生成上板位流。
4. 上板出现花屏、错帧或协议故障时，按位流哈希回退到 `stage3_frame_pool_gate_fix`，使用四客户端计数和最后成交突发信息定位故障。
